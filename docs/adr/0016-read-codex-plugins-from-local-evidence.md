# Read Codex Plugins from local evidence

A scan reads installed Codex Plugins from the Codex configuration file and the Codex plugin cache, and does not run the Codex executable. Earlier releases treated `codex plugin list --json` as the authority for installed state. Codex CLI 0.167.0 sends a request to a remote plugin catalog each time that command runs, and no option prevents the request. That request breaks the rule that a scan uses no network access. It also made the scan time depend on the network: with a stalled connection, one scan took about 30 seconds. The reply added entries with the source kind `remote`, and the strict parser then rejected the full listing.

A Codex Plugin is installed when `config.toml` contains a `[plugins."<name>@<marketplace>"]` table and the plugin cache contains one or more version directories for that Plugin. The table gives the enabled state, and a missing `enabled` value means enabled. Lampwright manages only these Plugins. The remote plugins that the Codex desktop app enables have no Plugin table, so they never become a Plugin, an Installation, or a plan target. Their cache directories stay non-removable findings.

The active version follows the selection that Codex CLI 0.167.0 showed in an isolated Codex home. Only real directories count. The directory `local` wins. Otherwise the greatest name wins: semantic version order applies when both names are semantic versions, and string order applies to all other pairs. A version link is a candidate only when no real directory exists, so that the cache safety check can report it and block removal.

The source tree of a Plugin comes from the marketplace manifest. A `local` marketplace uses the directory in its `[marketplaces.<name>]` table. A `git` marketplace uses the Codex clone at `.tmp/marketplaces/<name>` in the Codex home. That clone path is a Codex implementation detail. When the path or the manifest is absent, the Plugin stays installed and the Inventory loses only the source-artifact findings for that source tree.

A configuration file that is absent gives no Codex Plugins. A configuration file that is linked, hard-linked, unstable, or not valid TOML also gives no Codex Plugins, and each cache version becomes a non-removable finding with the state `invalid-configuration`. Earlier releases still reported the Plugin in that condition, with Managed Removal unavailable. A Plugin table that names a Plugin with no cache directory gives no Plugin.

The decision has three consequences. Lampwright interprets Codex files directly, so a change to the Codex file layout can make the scan wrong until Lampwright follows the change. Lampwright does not require that a configured marketplace still lists the Plugin, although Codex does. A Plugin that Codex no longer lists can thus appear in the Inventory, and its Managed Removal can then fail without a fallback. Managed Removal still runs `codex plugin remove` after the user approves a plan, as [ADR 0002](./0002-managed-removal-before-recoverable-fallback.md) requires.
